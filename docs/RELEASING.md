# Releasing CubeLite

Releases are fully automatic: merging a version bump to `main` builds, tags, and publishes everything. No manual tagging.

## Checklist (one PR)

1. **Bump versions** (keep them aligned):
   - `Cargo.toml` → `[workspace.package] version` — **this is the trigger and the source of truth for the tag**
   - `apps/desktop/src-tauri/tauri.conf.json` → `version`
   - Xcode project → `MARKETING_VERSION` for the cubelite target
   - refresh the lockfile: `cargo update --workspace`
2. **CHANGELOG.md**: rename `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD` and start a fresh empty `## [Unreleased]` above it. This section becomes the release notes.
3. Open the PR, merge to `main`. Done.

## What automation does on merge

`release.yml` fires on any `main` push that touches `Cargo.toml`:

1. **version** job reads the workspace version; if release `vX.Y.Z` already exists the run ends there (so unrelated `Cargo.toml` edits are free).
2. Builds:
   - native macOS app (Release, ad-hoc signed) → `CubeLite-macOS.dmg` / `.zip`
   - Tauri desktop bundles on macOS/Linux/Windows → `CubeLite-Desktop-*`, plus the
     updater artifacts (`.app.tar.gz` / `-setup.exe` / `.AppImage`) and their
     `.sig` signatures (see **Desktop auto-updater** below)
3. **publish-release** creates the `vX.Y.Z` tag *and* the GitHub Release in one step (`gh release create --target`), with the CHANGELOG section as notes, `SHA256SUMS.txt`, `latest.json` (updater manifest), and **stable asset names** (`releases/latest/download/…` links never change). Versions containing `-` (e.g. `0.4.0-beta.1`) are marked pre-release. A failing desktop platform does **not** block the release; the macOS native build is the gate.
4. **Pages redeploy** is dispatched explicitly at the end (releases created by the workflow token don't emit triggering events), so the site's docs and version badge refresh.

`workflow_dispatch` on `release.yml` is the manual escape hatch: run it from the Actions UI to (re)attempt a release of the current `main` version.

## Desktop auto-updater (#250)

The desktop app (Tauri) checks `https://github.com/<repo>/releases/latest/download/latest.json`
for updates (`tauri-plugin-updater`). That file is generated by CI, not hand-written.

- **Signing key**: updater artifacts are signed with a minisign keypair
  generated via `tauri signer generate` (independent of Apple's Developer
  Program). The **private key** lives only in the GitHub Actions secret
  `TAURI_SIGNING_PRIVATE_KEY`, consumed by the `build-desktop` matrix job in
  `release.yml`. The **public key** is committed in
  `apps/desktop/src-tauri/tauri.conf.json` (`plugins.updater.pubkey`).
  - **Backup**: the private key is *not* recoverable from anything in the
    repo or on GitHub. Whoever generates it is responsible for keeping an
    offline backup (e.g. a password manager or encrypted vault) — GitHub
    secrets are write-only, so if it's lost there's no way to retrieve it.
  - **Rotation consequences**: rotating the key (new `tauri signer generate`
    + new secret + new `pubkey` in `tauri.conf.json`) means every
    already-installed app checks its update manifest with the *old* pubkey
    embedded at build time. Those installs will fail signature verification
    on the next update and stop auto-updating silently — users on old
    versions must reinstall manually. Only rotate if the key is
    compromised, and call it out loudly in release notes when you do.
- **`latest.json` flow**: `scripts/make-latest-json.mjs` runs in the
  `publish-release` job after artifacts are downloaded and release notes are
  composed. It scans the merged `assets/` directory for the required updater
  targets — `darwin-aarch64` (`.app.tar.gz`), `linux-x86_64` (`.AppImage`),
  `windows-x86_64` (nsis `-setup.exe`, falling back to `.msi`) — pairs each
  with its `.sig`, and writes `assets/latest.json` in the Tauri v2 manifest
  format. (`darwin-x86_64` isn't emitted: the macOS matrix job builds only
  on Apple Silicon runners with no `--target` flag, so there's no universal
  or Intel build to point at today.) If a target's artifact or `.sig` is
  missing, the script exits 1 with a specific message — the workflow step
  is `continue-on-error: true`, so a broken platform doesn't hold the whole
  release hostage: the release still publishes, just without `latest.json`
  (i.e. without update support) until someone fixes the missing platform
  and runs `gh release upload vX.Y.Z latest.json` by hand. Watch the
  `publish-release` job's `::warning::` annotation for this case.
  - Fixture test: `node scripts/make-latest-json.mjs --check scripts/fixtures/updater/happy|missing-sig`
    is run in `ci.yml`'s "Test Frontend" job on every push/PR, so a
    regression in the scanning logic fails CI before it ever reaches a
    release.
- **Gatekeeper is unchanged**: the updater's minisign signature only
  protects the *update channel* (verifying the downloaded bundle came from
  us and wasn't tampered with) — it has nothing to do with macOS Gatekeeper
  or Windows SmartScreen. The app is still ad-hoc signed, not
  notarized/Developer-ID signed, so the first-install warning documented in
  the [installation guide](https://massimilianolapuma.github.io/cubelite/docs/installation.html)
  is unchanged until #121 lands.

## After the release

- Verify the download links on <https://massimilianolapuma.github.io/cubelite/> resolve to the new version.
- If a desktop platform job failed, fix it, then upload the missing asset to the existing release (`gh release upload vX.Y.Z <file>`).
- If `latest.json` was skipped (see **Desktop auto-updater** above), generate
  it locally once the missing platform's artifact/sig are uploaded:
  `node scripts/make-latest-json.mjs --dir <dir-with-all-assets> --tag vX.Y.Z --repo massimilianolapuma/cubelite --out latest.json`,
  then `gh release upload vX.Y.Z latest.json`.
